01

What is Redis?

INTERVIEW DEFINITION
Redis = Remote Dictionary Server

Redis is a fast, in-memory data store commonly used for caching, sessions, rate limiting, Pub/Sub and temporary application state.

It can also provide persistence, replication, clustering and other capabilities, but in a typical backend architecture Redis is often introduced to provide very low-latency shared access to frequently used data.

Why is Redis fast?

  • Primary data access happens in memory.
  • Simple data structures reduce processing overhead.
  • Efficient network protocol and optimized implementation.
  • Operations are generally very low latency.
  • Useful when an application needs extremely frequent reads/writes.
⭐ Key interview point Redis is usually not the replacement for your primary database. In a cache-aside architecture, MongoDB remains the source of truth while Redis provides faster access to frequently needed data.

Cache

Store frequently accessed data temporarily to reduce database latency and load.

Sessions

Store shared session state so multiple Node.js instances can access it.

Rate Limiting

Maintain distributed counters for API request limits.

Pub/Sub

Send real-time, non-durable messages through channels.

Temporary State

OTP, temporary tokens, verification state and short-lived workflows.

Distributed Coordination

Redis can support selected distributed coordination patterns when designed carefully.

03

TTL — Time To Live

TTL defines how long a Redis key should remain available.

After the configured lifetime expires, Redis can automatically remove the key. TTL is especially useful for data that should naturally disappear.

Why use TTL?

  • Prevents temporary data from living forever.
  • Controls cache freshness.
  • Automatically removes expired sessions or tokens.
  • Helps control memory usage.

OTP

Store OTP for a short period such as a few minutes, then automatically expire it.

Session

Expire inactive sessions after a configured period.

Cache

Keep product or loan configuration cached for a suitable freshness window.

Temporary Token

Short-lived verification or reset token can automatically expire.

Interview answer: TTL is a time limit attached to a Redis key. It is useful for temporary data such as OTPs, sessions, tokens and cache entries because Redis can automatically expire them.

Cache Hit vs Cache Miss

Cache Hit ✅

The requested data exists in Redis and is returned directly without querying the primary database.

Cache Miss ❌

The requested data is not in Redis, so the application retrieves it from the primary database, then may cache it for future requests.

Cache Hit

1API receives request.
2Redis contains the key.

Cache Miss

1API receives request.
2Redis does not contain the key.
3Query MongoDB.
4Store result in Redis and return it.
Why maximize cache hit ratio? A high hit ratio means more requests are served from Redis, reducing MongoDB load and usually reducing response latency. A cache is useful only when the cost of maintaining it is justified by the performance benefit.
05

Cache-Aside Pattern

Most important Redis caching pattern for interviews

In cache-aside, the application owns the cache logic. It checks Redis first, falls back to MongoDB on a miss, then places the result into Redis.

Client
→
Node.js
→
Redis
→
Return
On a cache miss: Redis → miss → MongoDB → result → Redis with TTL → response.

Typical request flow

  1. Receive REST API request.
  2. Build a deterministic Redis cache key.
  3. Check Redis.
  4. If hit → return Redis value.
  5. If miss → query MongoDB.
  6. Store the result in Redis with TTL.
  7. Return response to client.

Critical architecture rule

MongoDB = source of truth

Redis = fast access layer

If Redis disappears, cacheable data should generally be recoverable from MongoDB. The exact fallback strategy depends on the application's availability requirements.

06

Cache Invalidation

Cache invalidation = making stale cached data unavailable or replacing it.

The difficult part of caching is often not reading data—it is keeping cached data consistent enough with the source of truth.

Strategy How it works Useful when
TTL Allow the cached value to expire automatically. Slightly stale data is acceptable.
Delete after DB update Update MongoDB, then invalidate the Redis key. You want the next read to reload fresh data.
Update cache Update MongoDB and corresponding cached value. You need the cache to reflect changes immediately.
Versioned keys Use a version or generation in the key to move consumers to new data. Large-scale or controlled cache migrations.
Stale cache problem: If MongoDB contains new data but Redis still contains the old value, users can receive stale responses. Your invalidation strategy should match how much staleness the business can tolerate.

🎤 One-sentence answer

“Cache invalidation means ensuring stale cached data is removed or refreshed; I would typically combine TTL with explicit invalidation after important database updates.”

Good use cases

  • Live UI updates.

Critical limitation ⚠️

Traditional Redis Pub/Sub is not a durable message queue.

If a subscriber is disconnected when a message is published, that subscriber can miss the message.

Redis Persistence — RDB vs AOF

Redis is primarily an in-memory store, but it can persist data to disk. Two important persistence mechanisms are RDB and AOF.

RDB AOF
Meaning Point-in-time snapshots. Records write operations for reconstruction.
Typical advantage Compact files and efficient recovery. Can provide lower potential data loss with appropriate configuration.
Trade-off Changes since the latest snapshot can be lost. More disk I/O and larger persistence footprint can occur.
Best thought of as Snapshots. Write history / log.
Interview nuance: Persistence improves Redis's ability to recover data, but Redis should not automatically be treated as the durable source of truth for business data just because persistence is enabled.

Redis Cluster

Cluster = distribute data across multiple Redis nodes.

Redis Cluster provides sharding. Instead of requiring one Redis node to hold the complete dataset, key ranges are distributed across cluster nodes.

ApplicationNode.js instances
↓
Redis Node AShard / data subset
Redis Node BShard / data subset
Redis Node CShard / data subset

Benefits

  • Data sharding.
  • More aggregate memory capacity.
  • Horizontal scaling.
  • Potentially higher throughput.

When would you consider it?

When a single Redis node cannot comfortably handle the required dataset size, throughput or scaling requirements.

Redis vs MongoDB vs Kafka vs RabbitMQ

Technology Primary role Strength Choose it when...
Redis In-memory data store / cache / shared state Very low latency You need fast temporary/shared data access, caching or counters.
MongoDB Persistent document database Durable application data You need the primary source of truth for document-oriented business data.
Kafka Distributed event streaming Durable streams and replay You need high-throughput durable events, replay and stream processing.
RabbitMQ Message broker / queues Routing and work distribution You need queueing, acknowledgements and flexible message routing.
Do not say: “Redis is a faster MongoDB.”
Better: “Redis and MongoDB solve different problems. MongoDB can be the durable source of truth, while Redis can be a low-latency cache or shared state layer.”

Redis vs Node.js In-Memory Cache

Aspect Node.js process memory Redis
Location Inside one Node.js process. Separate shared service.
Multiple servers Each server has different cache. All servers can access shared cache.
Restart Process memory is lost. Redis has independent lifecycle and can be configured for persistence.
Horizontal scaling Requires additional cache coordination. Designed to act as shared infrastructure.
Operational complexity Very low. Requires running and monitoring Redis.
Rule of thumb: If you have one simple process and tiny cache requirements, local memory may be enough. Once you have multiple application instances and need shared state, Redis becomes much more useful.
16

What Happens if Redis Goes Down?

For cache data

If MongoDB remains available, the application can fall back to MongoDB for cacheable data and optionally rebuild the Redis cache.

For shared state

Impact depends on what Redis stores. Session, rate-limit or temporary workflow functionality may need a different fallback or HA design.

⚠️ Biggest risk: cache stampede If Redis fails and thousands of requests simultaneously fall back to MongoDB, MongoDB can suddenly receive a huge traffic spike.

High Availability

Use appropriate Redis HA architecture and failover.

Monitoring

Monitor memory, latency, connections, errors and hit ratio.

Controlled Fallback

Protect MongoDB using rate controls, request coalescing or other safeguards where appropriate.

17

Redis Memory Full & Eviction

Redis memory is finite.

When configured memory limits are reached, Redis needs a defined strategy for handling new writes. Eviction policies determine which keys can be removed.

Why eviction can be acceptable

For a cache, the Redis copy is not the source of truth. If an old cache entry is evicted, the application can usually fetch the data again from MongoDB and repopulate Redis.

Why policy matters

The eviction policy should match the workload. A cache workload may prefer removing less useful keys, while workloads containing important non-cache data require more careful planning.

Interview point: Never answer “Redis automatically deletes random data when memory is full.” Explain that memory limits and an appropriate configured eviction policy determine what happens.
18

Multi-Region Redis

In a multi-region application, you may have Redis infrastructure close to users in different regions. This can reduce cross-region latency, but it introduces architectural complexity.

Latency

Keep requests close to users where possible.

Replication

Consider how data moves between regions.

Consistency

Decide how much cross-region staleness is acceptable.

Failover

Plan what happens when an entire region fails.

Data Residency

Regional regulations may affect where data can be stored.

Complexity

Multi-region systems require more operational and consistency planning.

Interview answer: “I would not introduce multi-region Redis just for the sake of scale. I would first establish the latency, availability and data-residency requirements, then choose an appropriate replication and failover strategy.”

At a simplified steady-state level, a 95% hit rate means roughly 9,500 requests/second can be served from the cache and about 500 requests/second need a database fallback. Real systems need to account for request patterns, misses, writes, hot keys, bursts and failures.

Scaling strategy

  • Keep Node.js instances stateless where possible.
  • Use shared Redis for cache and distributed state.
  • Use Redis Cluster when one Redis node cannot meet memory or throughput requirements.
  • Use replication/HA where availability requirements demand it.
  • Use suitable MongoDB scaling independently.

Production concerns

  • Monitor cache hit/miss ratio.
  • Monitor Redis latency and memory.
  • Plan for Redis failure.
  • Prevent cache stampedes.
  • Use TTLs appropriately.
  • Design cache keys carefully.

🎤 Strong interview response

“For 10,000 requests per second, I would put multiple stateless Node.js instances behind a load balancer and use Redis as the shared caching layer. I would use cache-aside so Redis handles frequent reads while MongoDB remains the source of truth. I would use TTLs and an explicit invalidation strategy, monitor hit ratio and Redis latency, and introduce Redis Cluster if the memory or throughput requirement exceeds a single node. I would also design a controlled MongoDB fallback and protect against cache stampedes if Redis fails.”

Redis in a Loan Origination System

Architecture exercise: Redis could be introduced into a Loan Origination System for selected high-frequency or short-lived data. This does not imply that Redis is already implemented in the system.

Loan/Product Config

Cache frequently accessed loan-product configuration when the data changes relatively infrequently.

Verification State

Store short-lived temporary verification state where appropriate.

Rate Limiting

Protect KYC, eligibility or other APIs from excessive requests.

Session State

Share session information across multiple backend instances.

Short-lived Responses

Cache expensive API responses for a short period when business rules permit.

Temporary Workflow Data

Store transient information that does not need to become the durable system of record.

Financial-system caution: Loan applications, KYC records and other critical business data should have an appropriate durable source of truth and consistency model. Redis should not be casually made the only copy of critical data.

🎤 How would you use Redis in an LOS?

“I would consider Redis for frequently accessed loan-product configuration, short-lived verification state, API rate limiting, sessions and selected cacheable responses. I would keep the durable loan and customer data in the primary database and use TTL plus explicit invalidation to manage cached data.”

21

When NOT to Use Redis

❌ Rarely accessed data

If data is rarely read, adding a cache may not provide enough benefit to justify the complexity.

❌ No meaningful latency benefit

If the database is already fast enough, Redis may add unnecessary infrastructure.

❌ Primary durable source of truth

Do not automatically choose Redis as the only durable store for critical business data.

❌ Very difficult invalidation

If consistency requirements make cache invalidation extremely complex, reconsider whether caching is worth it.

❌ Durable event streaming

For durable event streaming, replay and large-scale event processing, Kafka may be a better fit.

❌ Operational overhead

Every new infrastructure component needs monitoring, security, capacity planning and failure handling.

60-Second Redis Interview Answer

🎤 Memorize the structure, not every word

“Redis is an in-memory data store commonly used as a low-latency cache and for shared application state. In a Node.js and MongoDB application, I would commonly use the cache-aside pattern: first check Redis, return the value on a cache hit, and on a miss query MongoDB, store the result in Redis with an appropriate TTL, and return it. MongoDB remains the source of truth.

Redis can also be used for distributed sessions, rate limiting, temporary tokens and transient Pub/Sub notifications. For cache consistency, I would combine TTL with explicit invalidation or cache updates depending on the business requirement.

For availability, Redis supports replication and failover-oriented architectures, while Redis Cluster provides sharding for horizontal scaling. Replication means copies of data; clustering means distributing data across nodes. If Redis fails, I would use an appropriate fallback for cacheable data, but I would also protect MongoDB from a cache stampede. Finally, I would not use traditional Redis Pub/Sub when durable message delivery is required; Kafka or a queueing system may be more appropriate.”
